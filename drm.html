DRM progress

How LG's video_player_drm plugin plays protected video on webOS 26, what an older TV lacks, and where each route stands on webOS 6.

Last updated 20 November 2026. Tested on an LG C1 with webOS 6.5.3.

How it works on webOS 26

The plugin itself is simple. The TV's media server does almost all the work. This section is based on LG's plugin source; the media server's inner steps are inferred, not traced on a webOS 26 TV.

  1. Window. The Flutter embedder creates an exported window, a place on screen for a hardware video layer, with an id such as _Window_Id_3.
  2. Bind. The plugin calls NDL_MediaInitWithWindowId(windowId).
  3. Load. The plugin calls NDL_MediaLoadWithOption(url, option). The option carries appId, windowId and drm: {type, licenseUrl, useLicenseCallback}.
  4. Licence. With a licence URL, the media server fetches the licence itself. With a licence callback, it sends a drmEncrypted event with the challenge; the plugin asks the Dart side (requestDrmLicense) and returns the licence through NDL_MediaSetDrmOperation(..., "update", ...).
  5. Decrypt and decode. The media server downloads the stream, decrypts on the secure video path and decodes in hardware.
  6. Display. The media server connects the decoder output to the exported window. The embedder places that window where the VideoPlayer widget is and leaves a transparent hole in the UI.
  7. Events. loadCompleted, playing, currentTime, videoInfo and the rest go back to the plugin through the NDL event callback.

On webOS 6, LG's own apps get Widevine another way: web apps use the browser's built-in DRM in LG's Chromium, and the YouTube app calls the CDM and the TV's player library directly. The media path that Flutter apps use has no Widevine.

Widevine routes on webOS 6

A. Software proxy (L3)

Works, opt-in Enabled with compat-widevine-cdm.

The TV's software CDM gets the licence, by URL or through the licence callback. A proxy on 127.0.0.1 decrypts the media and hands the media server a clear stream. Seeking and adaptive bitrate switching work, and the picture shows.

Limit: software security. Services that require hardware security reduce quality or refuse to play.

B. Hardware route (L1)

Experimental Switch compat-widevine-l1. Not in a release yet; the code is on the widevine-l1 branch until the picture shows.

Takes the same approach as the YouTube app: the TV's hardware CDM wrapper packs each sample for the secure video path, and the TV's player library (StarfishMediaAPIs) decodes it. The video is never decrypted inside the app.

Our own code reads the DASH manifest and MP4 segments and sends the plugin the same events it gets from the media API.

The missing step: attaching the video to the screen

The DRM test reported playback as passing, because the position kept advancing, but a person watching the TV saw only black. On webOS 26, and with the media API on webOS 6, the media server owns the player and connects its output to the screen and the exported window. The hardware route runs the player inside the app, so nothing makes that connection yet.

The exact call isn't known yet. The TV's player library has several candidates:

  • load options autoConnect and avSink.videoSink.type;
  • StarfishMediaAPIs::setWindowId();
  • its own connection code, which logs "Connection Failed.". Right after loading, the player sends an event naming the main video and sound outputs, followed by one with code 8, most likely that failure.

The YouTube app uses the same library and shows its picture, so the right settings exist. Next steps:

  1. Turn on the player's debug log and read why the connection fails.
  2. Compare with the load settings and calls the YouTube app uses.
  3. Make the DRM test fail on a black screen. Screenshots can't show protected video, so the test will check the video output's connection state instead of only the playback position.

Both Widevine routes use the TV's own CDM outside the terms LG and Google ship it under, and the device certificate could be revoked. Don't enable them in a published app without legal advice.
